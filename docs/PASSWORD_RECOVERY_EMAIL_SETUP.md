# RFP Monitoring System — branded password recovery

## Active application recovery workflow

This application now sends **branded password recovery emails through the RFP
server SMTP configuration** rather than the generic Supabase Auth mailer.

1. Staff opens `/admin/forgot-password`.
2. The form submits to `POST /api/auth/recover` over the RFP website origin.
3. The server rate-limits the request and checks for an active staff profile.
4. Supabase Auth's **admin.generateLink(type: recovery)** produces a signed,
   single-use recovery link. The token stays on the server and is never returned
   to the browser.
5. RFP's authorized SMTP transport emails a branded HTML message with the
   subject `RFP Monitoring System | Reset your password` and display sender
   **RFP Monitoring System**. The sender *address* is taken from the already
   approved `SMTP_FROM_EMAIL` setting.
6. Clicking the link takes the user to `/admin/reset-password` to set a new
   password using the regular Supabase Auth SDK.

**The RFP SMTP settings in Vercel must be present**, as they are for the
existing workflow emails:
`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`,
`SMTP_PASSWORD`, `SMTP_FROM_EMAIL`, and `SITE_URL`.
The approved From address must be authorized by the SMTP provider.
Do not share or hardcode credentials.

No Supabase hosted custom SMTP or hosted Auth template change is required
for **this website's password recovery form**. Other built-in Supabase emails,
such as account invitations, may still use Supabase's own email templates and
provider unless separately configured.

## Security controls

- Email registration status is not disclosed by the API or UI.
- Only active staff profiles may receive reset messages.
- Rate limits use the existing atomic PostgreSQL submission limiter with
  separate HMAC namespaces: **10 attempts per IP per hour** and
  **3 attempts per normalized email per hour**.
- Recovery links are HTTPS, generated by Supabase Auth, and not stored or logged.
- The original From address is preserved while its display name becomes
  **RFP Monitoring System**.
- Sensitive SMTP and Supabase administrative credentials remain server-only.
- A failed SMTP send returns a generic availability error.
- The reset-password screen uses `supabase.auth.updateUser({ password })`;
  after a successful reset the browser signs out, requiring a fresh login.

## Configuration and testing

1. Confirm the latest `main` commit is successfully deployed to the
   `greenlight-rfp` Vercel project.
2. Confirm the existing RFP workflow email queue can send mail through
   the approved SMTP account.
3. Confirm `https://greenlight-rfp.vercel.app/admin/reset-password` is
   allowlisted under [Supabase Authentication URL Configuration](https://supabase.com/dashboard/project/chchtjolsnlelgxbgkip/auth/url-configuration).
4. Use a designated internal staff test account; do not trigger password
   resets for arbitrary real users.
5. Verify the **From** display name, the approved sender address, the
   subject, and the responsive design in the received email.
6. Click the secure link, set a new password, and verify the new login works.
7. Check that an unknown account gets the same confirmation response but no mail.
8. Test repeated requests to confirm the per-account and per-IP limits.

Automated tests run without generating real password links or sending emails.
An actual end-to-end email test requires an approved recipient's inbox.

## Optional: branded Supabase Auth emails outside the website form

For direct Supabase-generated Auth emails and account invitations,
the repository includes:

- `supabase/templates/recovery.html`
- `supabase/config.toml` (local CLI template only)

On a hosted Supabase project, those are not automatically installed from
GitHub. If direct Supabase Auth branding is later needed, configure a custom
SMTP provider in the Supabase Auth Dashboard, then paste the HTML and subject
into the hosted Recovery template. The RFP Supabase project is on the
Free plan and was created after the June 3, 2026 template restriction.
This **optional** step is not necessary for the website's branded reset flow.

## Troubleshooting

If the recovery form displays "Email recovery is temporarily unavailable",
check RFP SMTP server variables in Vercel, the provider's sender
authorization, and server logs. If the application has not deployed due
to a Vercel build-rate limit, the older Supabase Auth sender flow may
still be live. Do not assume GitHub's `main` state equals a production deploy.
